# 安全修复 harness 设计

状态：设计稿（2026-10-24）。**替代** [worker-agent-design](worker-agent-design.md) 中「工作机常驻编码 agent 取代开发」的方向；该文档保留作历史参考。相关：[harness 设计](harness-design.md)、[浏览器实验](browser-spike.md)、[工作机原型](../worker/desktop/README.md)。

## 0. 定位

**不取代开发，只做安全：发现漏洞 → 判断和我们有没有关系 → 找到官方修复版本 → 改版本、提 MR → CI 重新构建 → 复核线上确实修好。**

为什么收窄：

1. **平台覆盖不了**：桌面端、Android、iOS 需要各自的系统和工具链，一台 Linux 不够；通用开发的需求、交互、产品判断也离不开人。
2. **安全修复可验证**：复扫不再有这个 CVE、CI 通过、线上跑的是新版本——三件事都能由程序核对。通用开发做不到这一点。
3. **平台问题在安全场景里消失**：agent 只改依赖声明（版本号、锁文件、基础镜像、chart 版本），构建和测试交给 CI；你们的 CI 已经有对应平台的构建环境。

和本地用法一样：agent 缺的只是「把代码改对」这一小段，改完**自己审一遍 diff、跑一遍测试**，再交给人批准合并。

## 1. 范围

| 做 | 不做 |
|---|---|
| 漏洞情报采集、去重、补全 KEV/EPSS | 通用功能开发、重构 |
| 资产清单：线上镜像与版本、基础设施组件版本、仓库依赖 | 编译桌面端/移动端产物 |
| 漏洞 ↔ 资产匹配、分诊、优先级 | 让 agent 自行合并或部署 |
| 修复方案：官方修复版本、升级类型、风险说明 | 绕过 CI 或人工审批 |
| 改依赖声明 / 基础镜像 / chart 版本，自审 + 测试后提 MR | 官方没有修复时擅自打补丁 |
| CI、复扫、ArgoCD 线上版本核对，台账闭环 | |
| 飞书分析报告（定时 + 按需） | |

「电脑」在这里只是**能力提供者**：查资料（联网搜索、读网页）、运行包管理器重新生成锁文件、本地复扫；不再是写代码、编译的开发机。桌面、编码 agent 适配器、microVM 全部移出范围。

## 2. 流水线

```text
① 情报      KEV · GHSA · Kubernetes CVE feed · 厂商公告 · oss-security · 社区   （已实现）
              ↓ 去重入台账，补 KEV / EPSS / CVSS
② 资产      ArgoCD 应用 → 线上镜像:tag      （已有只读工具，待做成清单）
            Harbor 镜像扫描（Trivy）结果     （待核实是否开启）
            基础设施组件版本：k3s/VKE、ingress-nginx、ArgoCD、GitLab、Harbor、CNPG …
            源码仓依赖清单：锁文件 / go.mod / requirements / pom / gradle / Dockerfile FROM
              ↓
③ 匹配      包生态 + 包名 + 版本区间（OSV/GHSA 的 affected 范围）→ 确定性匹配
            产品名（基础设施组件）→ 候选匹配，需模型或人确认版本
              ↓
④ 分诊      规则打分：线上在跑？对外暴露？KEV？EPSS？CVSS？有修复版本？→ P0~P3
            暴露面（已实现）：Service/Ingress 推算 公网 / 经公网入口间接 / 仅内网 / 仅集群内 / 无入口；
            不对公网开放的降一级（数据库、缓存不算间接暴露），远端集群可在 kv asset_exposure_overrides 补充
            模型写理由与影响面，不改分数规则
              ↓
⑤ 修复方案  官方修复版本（OSV/GHSA fixed）· 升级类型（补丁/小版本/大版本）· 修复路径
              ↓
⑥ 变更      改依赖声明 → 重新生成锁文件 → 自审 diff → 测试 → 审批 → MR
              ↓
⑦ 验证      CI 通过 → 新镜像复扫无该 CVE → ArgoCD 线上为新 tag 且健康 → 台账 fixed
```

### 2.1 修复路径

| 情况 | 修复动作 | 谁来做 |
|---|---|---|
| 补丁/小版本已修复 | 改版本号、重新生成锁文件 | 确定性代码为主 |
| 间接依赖 | overrides / resolutions / replace，或升级上层依赖 | 模型选方案，代码执行 |
| 只有大版本修复 | 读变更日志，评估破坏性改动；需要改业务代码时**只出方案不改**，转给开发 | 模型分析，人决定 |
| 基础镜像/系统包 | 改 `FROM` 到修复后的 tag 或 digest | 确定性代码 |
| 集群组件/chart | 改 gitops 仓的 chart 版本或镜像 tag | 现有 `code_*` + GitOps 静态校验 |
| 无官方修复 | 缓解（配置、关闭功能、网络策略）或记录接受风险 | 模型写建议，人决定 |

### 2.2 自审与测试（提 MR 前，全部可核对）

- **diff 白名单**：只允许依赖声明、锁文件、Dockerfile `FROM`、chart 版本字段变化；出现其他文件或业务代码改动则停止。
- **版本核对**：diff 里的新版本 = 修复方案里的修复版本；没有引入方案外的新包；锁文件哈希完整。
- **测试**：仓库登记了测试命令的，在隔离沙箱运行；需要访问包仓库时由能力层（工作机 shell，经出境代理）执行；结果绑定代码快照。
- **复扫**：能在 MR 阶段复扫的（`trivy fs` 或 CI 里的扫描作业），确认目标 CVE 消失、没有新增高危。
- 以上任一不过：不提 MR，报告里说明卡在哪一步。

### 2.3 台账状态

```text
new → triaging → not_affected（附依据）
               → affected → fix_planned → mr_open → merged → deployed → fixed（复扫通过）
               → affected → no_fix → mitigated / accepted_risk（附理由与复查日期）
```

`fixed` 只能由第 ⑦ 步的确定性核对写入，模型不能直接标记。

## 3. 飞书分析报告

| 类型 | 触发 | 内容 |
|---|---|---|
| 日报 | 每天定时 | 新增且与资产相关的漏洞、优先级、受影响服务、建议动作、进行中的 MR |
| 周报 | 每周 | 存量风险趋势、超期未修、已修复核对结果 |
| 按需 | 群里 @ 机器人 | 「分析 CVE-xxxx」「我们受不受 xxx 影响」「出一份最近 7 天的漏洞报告」 |
| 即时告警 | 匹配到 P0（KEV + 线上在跑 + 暴露） | 单条卡片，附修复方案与一键发起修复 |

报告里每条结论都要带证据：情报来源链接、资产来源（哪个 ArgoCD 应用、哪个镜像 tag、哪份锁文件）、匹配依据（版本区间）。与资产无关的全球漏洞只计数，不展开。

## 5. 分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| S0 现在 | 用现有工具在飞书里按需出漏洞分析报告，观察质量与缺口 | 一份报告能区分「和我们相关 / 无关」，结论带证据 |
| S1 资产与匹配 | 资产清单（ArgoCD 镜像、基础设施组件版本）落库并定时刷新；版本区间匹配；分诊打分；日报 | 台账中与资产相关的条目被自动标出，日报不出现无关的全球漏洞 |
| S2 Harbor | 接入 Harbor 扫描结果作为镜像层面的漏洞来源；与情报交叉 | 每个线上镜像能看到其 CVE 列表与修复版本。**代码已完成**（ops/harbor、image_scan、vuln_report.image_findings、image_vulns）；待 Harbor 启用 Trivy 并提供只读 robot 后实测 |
| S3 修复 | **已完成第一段（只读方案）**：`vuln_fix_plan`——第三方镜像在 gitops 的引用位置、Docker Hub 同线最新 tag、停止维护提示、修改步骤；自研镜像只定位问题：线上提交号 + 按包类型推断该改的清单（composer/go.mod/npm/maven/应用依赖）+ 需升级基础镜像/运行时的包，交给开发；不读业务仓库（技术栈由 Harbor Trivy 扫描得到，可选 kv `source_repo_read=1` 才经 GitLab 定位到文件行）。待做：依赖文件改写器（npm/pnpm、Go、pip/poetry、Maven/Gradle、Dockerfile、chart）、锁文件重新生成、自审、测试、MR | 3 个真实补丁级升级从发现到 MR 无人工改代码，diff 只含依赖变化 |
| S4 闭环 | CI 回写、复扫、ArgoCD 线上核对、台账状态机、周报 | 一个漏洞从入台账到 fixed 全程留痕，fixed 由程序核对写入 |

## 6. 能力层（原「工作机」）的保留部分

- 保留：`web_search` / `web_fetch`（读公告、变更日志）、`sandbox_run`（离线分析）、`box_shell`（需要访问包仓库的包管理器命令、`trivy` / `syft` 扫描）。
- 移出：桌面操作、有界面浏览器作为主路径、编码 agent 适配器、microVM。原型代码保留在 `worker/desktop/`，需要时作为能力提供。
- 原则不变：执行环境没有公司凭据、不能进内网；写令牌只在控制面；agent 不合并、不部署。
